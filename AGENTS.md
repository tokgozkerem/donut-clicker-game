# Donut Clicker Engineering Guide

## Project Overview

Donut Clicker is a free, single-player browser incremental/clicker game. The vanilla HTML/CSS/JavaScript frontend owns gameplay and player state; `localStorage` is the primary persistence system. `script.js` defines one `Game` class, instantiated on `DOMContentLoaded` and exposed as `window._game` for generated inline handlers. `game-content.js` loads first as an ordered deferred classic script and supplies fresh upgrade and building definitions. There is no frontend package manifest, framework, or build requirement.

The README and `CNAME` support static hosting/custom-domain assumptions. `backend/` contains a separate FastAPI/SQLAlchemy save-and-analytics API, but the frontend does not call it. Do not require or connect that backend to run the game. Live deployment configuration is not established by the repository.

## Core Engineering Rules

- Preserve player saves and supported old formats. Never erase/reinitialize stored progress as a routine error fallback.
- Do not change balance, economy, progression, or reset semantics during correctness work unless explicitly requested. Verify credited state/math, not only displayed numbers.
- Prefer authoritative shared logic over competing calculations. Trace callers, load reconstruction, live production, and offline credit before consolidating math.
- Keep the lightweight static-browser architecture unless asked otherwise. Do not introduce paid services, accounts, cloud infrastructure, or unnecessary dependencies.
- Keep focused changes narrow; avoid unrelated refactors. Do not infer historical design intent from names, comments, or unfinished UI promises alone.
- After persistence/economy changes, verify save compatibility, round trips, failure protection, and affected economic invariants. Syntax checks alone do not prove gameplay correctness.
- Keep this guide and project history aligned with observed code. Upcoming work is not implemented behavior.

## Save System Contract

### Console debug tools V3 isolation

- `script.js` owns a private `donutDebug` closure. The normal DOMContentLoaded bootstrap attaches it to the actual Game instance after `game.init()`, exposing only `window.openDonutDebug()`, `window.closeDonutDebug()` and `window.resetDonutDebug()`. These commands are source-discoverable development convenience, not authentication; no access setup or persistence.
- The dialog is created only on open. Close removes it while retaining the temporary manual-click multiplier; reset removes it and restores1. Reload also restores1. No owner flag, old API compatibility, shortcut/URL/name trigger, normal UI hint or recurring panel refresh.
- Only final manual click income is scaled, at1/10/100/1000/10000; canonical click math, CPS, combo/Auto Catcher rewards and every production system remain unchanged. The multiplier stays private memory state and never enters Game/save fields.
- Balance-only/earned grants use the existing settlement and `creditDonuts(amount, false/true)` authority, then existing progression/UI/checkpoint paths. Granted currency saves as normal progress; debug reset does not undo grants. SaveVersion1 and all persistence protections remain unchanged.

### Storage, formats, and version

- Primary: `gameState`; one backup: `gameStateBackup`, both in same-origin `localStorage`. Separate `bakeryName` and `feedbackClosed` keys also exist.
- New snapshots contain `saveVersion: 1`. This is distinct from `gameVersion` and envelope `v: 2`.
- `decodeSave()` trims text: leading `{` means legacy plain JSON; otherwise `decryptSave()` decodes the existing Base64 JSON envelope `{ v: 2, data, sig }` and verifies `generateChecksum(data)`.
- Despite the historical `encryptSave()` / `decryptSave()` names, this is encoding, not encryption. The unchanged non-cryptographic checksum detects some corruption; it provides no authenticity, secrecy, or anti-cheat protection. Legacy plain JSON has no checksum.
- `isValidSaveData()` validates core state, finite numbers, selected nested structures/settings, and unsafe object keys. Version 1 requires the defined top-level snapshot fields. Missing version or explicit version `0` takes the legacy compatibility path; missing optional legacy fields use defaults. Other explicit versions are rejected. There is no destructive migration or general migration framework.
- Mine/Ore and Baker Correctness add narrow **load-only** `decodeSave(raw, { recoverMineState: true, recoverBakerState: true })` paths: verify format/checksum and unsafe keys first, repair specified ore/ingredient inventory and market values on a copy, then run full structural validation. Strict decoding remains the default for new candidates and backup rotation. A primary needing these repairs must not overwrite a valid backup, and loading still rewrites neither slot. Other malformed systems or bad checksums are not repaired by this path.

### Write and backup flow

`saveGame({ silent = false })` cancels a pending checkpoint, requires `_saveReady`, refuses `saveWritesBlocked`, and rereads the primary for the stale-tab check described below. It then:

1. Collects durable state, encodes it with its checksum, and validates the encoded candidate through `decodeSave()` before modifying storage.
2. Skips storage writes if the candidate is byte-identical to the current primary.
3. Decodes/validates the previous primary. **Only a valid primary can rotate into `gameStateBackup`.** Skip the backup write if it already equals that primary.
4. If a required backup read/write fails, stop before replacing the primary. Otherwise write the new primary, then update `_loadedPrimarySave` and `_lastSaveTime`.

An invalid primary must never replace the last known-good backup. With no valid previous primary, saving does not rotate the backup. A primary-write failure leaves the previous primary intact and any successfully secured backup intact. Candidate serialization/validation failure leaves both slots untouched. One backup is a prior checkpoint, not a history archive or off-device backup.

### Loading and unrecovered-save protection

`loadGame()` holds `_saveReady = false` during restoration so nested durable actions cannot save partially hydrated state.

1. Read/decode/validate primary; prefer it when valid.
2. If missing, invalid, or unreadable, try backup.
3. A valid backup loads with a notification. Loading itself writes neither slot. A later successful save may replace the invalid primary while keeping the valid backup.
4. If both keys are absent and readable, fresh state can save normally.
5. If recovery fails and stored data exists **or storage could not be read**, set `saveWritesBlocked = true`; the game can continue in memory. Autosave, action checkpoints, lifecycle saves, **and manual Save** cannot overwrite the stored values.

Do not remove this block as an inconvenience: corrupted progress → fresh memory state → autosave must not permanently erase the recoverable evidence. Restore stored data and reload, or explicitly abandon it through confirmed Reset Game. Protection applies to the game snapshot; auxiliary preference keys are not both recovery slots.

Unexpected exceptions while applying validated state are caught and pause saving. They do not currently trigger another backup attempt or roll back partial in-memory hydration; this is a remaining edge case, not a guarantee of fully transactional loading.

Existing snapshots still include buildings, upgrade flags, quest state, recipes, currency/clicks/prestige, ores/workers/ingredients, `oreTypePrices` with histories/trends, `farmState`, `farmNextAnimalId`, `donutCoin`, bakery name, and `lastActiveTime`. Upgrade purchase flags remain indexed by array position: reordering upgrades can break compatibility.

Optional `timeState` is now authoritative: settled checkpoint, inactive-episode usage, Mine/Baker economic-cycle remainders and simulation RNG. `lastActiveTime` mirrors the settled checkpoint; legacy resource timestamps mirror checkpoint minus economic remainder. `restoreProductionCheckpoint()` remains a legacy adapter, not a second elapsed owner. ### Scheduling, durable actions, and lifecycle

- `init()` retains the **180,000 ms / three-minute autosave**. Its 60,000 ms throttle does not change that interval.
- `requestSave(delay = 1000)` coalesces nearby actions at the earliest pending deadline; later requests do not continually postpone it. Automatic `buyItem(key, true)` purchases request **15,000 ms** batching; a manual action can expedite that checkpoint.
- One-second requests cover successful building/upgrade purchases, crafting, quest claims, ore buy/sell/Sell All, volume/auto-buyer/bakery-name changes, animal purchases/releases/renaming, goods sales, care, feed configuration, breeding start/completion, contract accept/cancel/complete/reroll, and crate opening.
- Prestige calls `saveGame({ silent: true })` immediately after its existing reset. Manual Save, successful DonutCoin claims, and offline-modal collection/backdrop close also call `saveGame()` directly.
- Ordinary donut clicks, animation frames, and continuous passive/farm production do not save synchronously on each mutation. Batching reduces localStorage writes while reducing loss of recent deliberate actions.
- `setupSaveLifecycle()` settles active time before hide/pagehide, begins or continues the inactive episode, then checkpoints. Show/pageshow settle inactive time before returning to active and resetting the RAF accumulator. If no action save is pending and `_lastSaveTime` is less than one second old, the duplicate storage checkpoint may be skipped; settlement still happens. All save paths settle before serializing a new economic timestamp; `_savingTimeSettlement` suppresses nested save requests, and `_settlingTime` blocks recursive simulation. These remain best-effort lifecycle checkpoints, not crash/process-termination guarantees.

### Storage errors, tabs, and reset

`readStorage()`, `writeStorage()`, and `removeStorage()` catch exceptions, return failure, and use `warnAboutStorage()` / `_storageWarnings` to show each warning category once per instance. Gameplay can continue in memory. Write failures can be retried later; an unreadable startup cannot safely assume no save exists.

The stale-tab guard compares the **exact raw primary string**, not a numeric revision or timestamp, against `_loadedPrimarySave` captured during loading/last successful save. A change, including deletion/reset or a legacy writer's replacement, pauses this tab's writes before backup rotation. It does not merge progress or adopt another tab's state. If primary was unreadable but backup loaded, unknown primary contents are not authorized for replacement; reload after storage access returns.

This is optimistic protection, **not an atomic cross-tab transaction**. Simultaneous check/write sequences can race; tabs running pre-V1 code cannot enforce this guard.

`resetGame()` requires the existing confirmation, cancels pending saving, blocks the old instance, removes **backup first, then primary**, and aborts reload if either slot removal fails. It also attempts to remove `bakeryName`, then reloads. A fresh `Game` instance plus absent slots restores normal saving. Clearing both prevents deleted progress from returning through backup recovery; `feedbackClosed` is not cleared.

### Transient state and compatibility invariants

UI/panel state, active combo sessions and catch queues, animations, DOM caches, `purchaseAmount`, and `isBuying` / `isSelling` trading modes remain transient. Auto Catcher ownership persists through its upgrade flag, not through a running combo session.

Preserve these invariants: valid existing saves load; plain JSON and v2 checksum envelopes remain supported; missing legacy fields default safely; invalid primary cannot contaminate backup; unrecovered stored progress cannot be replaced by fresh autosave/manual Save; storage errors do not crash gameplay; reset deliberately clears both slots; durable state round-trips; persistence changes alone do not migrate production/economy rules.

## Authoritative Time Contract (Offline / Time Consistency V1)

Time is part of the economy. `settleTime()` is the sole elapsed-time owner. The RAF loop, economic mutation boundaries, visibility transitions, saving and loading all use it; no subsystem independently catches up a missing interval.

| System | Visible | Hidden / closed |
| --- | --- | --- |
| Main donuts, Mine ores/market/actions, Baker ingredients | 100% economic time | 25% economic time, maximum first 12 real hours of one inactive episode |
| Farm goods, care-cycle consumption, paid feed and contract work | Existing live modifiers at 100% economic time | Same modifiers/rules at 25%, same economic cap |
| Breeding/programs and cooldowns | 100% real elapsed | 100% real elapsed, including after the economic cap |
| Main temporary multipliers / Farm timed buffs | Real-time expiry; effect only on overlapping production | Same real-time expiry, production still reduced/capped |
| Care windows, quest deadlines/cooldowns, DonutCoin readiness | Wall-clock deadlines | Same deadlines; no automatic care or missed daily coin grants |
| Auto-buyer / combos / falling-donut catches | Visible-session interaction/automation only | No historical buys, spawns, catches or rewards |

- Persisted optional `timeState = { settledAt, inactive, inactiveElapsed, mineProgress, bakerProgress, randomState }`. `settledAt` never regresses. `inactiveElapsed` saturates at 43,200,000 ms and persists across hidden saves/reloads; only a genuine return to visible resets the episode. A save does not open another 12-hour credit window. Real timers continue after the economic cap.
- Same-page active economic elapsed uses `performance.now()`. Wall-clock persistence/deadlines use nonnegative wall elapsed and the non-regressing checkpoint. Forward wall adjustments age real timers without manufacturing active income; backward adjustments cannot replay economic time. Focus/blur is not a policy boundary; Page Visibility is. A surviving hidden tab and a restored closed game use the same settlement path.
- Segments split only at relevant events: policy cap, multiplier expiry/queued activation, resource-cycle boundaries, Farm buff/contract/breeding completion, storage/auto-collection/care-cycle/feed exhaustion and production-objective boundaries. Canonical `getProductionBreakdown(eventTime)` supplies all CPS. The old rate applies before a purchase/upgrade/craft/prestige/mastery/buff/action mutation; the new rate starts afterward. A reentrancy guard makes nested mutation settlement inert. The optional forced-seconds argument on `updateProduction()` remains a test/debug interval adapter, not a runtime catch-up path.
- Mine accumulates 60,000 economic ms per cycle and Baker 300,000. Consume complete cycles and retain exact fractional progress. Each Mine cycle produces five ores/worker, advances the unchanged market formula once and refreshes allowance to ten (never banked). Baker produces two ingredients/Baker. Global-cycle ownership semantics remain: settle before purchase, then current owners receive the next boundary batch; no worker acquisition proration.
- Time-generated random results use a persisted xorshift32 stream isolated from UI randomness. Ordinary batches retain existing draws/retry behavior. Batches above 1,000 units use sequential multinomial sampling (exact small binomial tails, normal approximation for large populations), conserving whole-unit totals and configured normalized probabilities/variance without millions of RNG calls. Market/Farm event draws use the same replay stream. Current contract-board refreshes use their own deadline-keyed seed so skipping unseen boards cannot perturb reward/resource RNG. No crafting/crate/market economic constants changed.
- Farm settlement reuses live production/modifier, care, storage, contract, breeding, XP and auto-collection paths; the old simplified offline Farm calculation is removed. Feed is charged only for actual producing economic time, pauses at full storage and falls back to Standard at exhaustion. Old buffs expire before new completion rewards start. Breeding completion starts its approved cooldown at the completion boundary; remaining away time reduces it normally. Automatic collection retains its existing payout/no-manual-XP/no-crate behavior.
- Care/contract-board opportunities advance from their real deadlines rather than from the next delivered frame. Missed care is not automatically performed. Existing active quest progress is checked chronologically; no historical replacement assignments are invented while inactive. Quest goals/rewards/lifecycle are unchanged; failure cooldown starts at the timed quest’s deadline, so delayed callbacks cannot postpone it. Progress/expiry entry points settle pending income before testing a deadline. Interaction donuts/queues are removed on hide; stale hidden callbacks cannot award catch income.
- Restore fully hydrates economic/quest/Farm state and freezes missing old completed rewards before advancing saved time. Legacy saves keep collections/ownership/rewards and gain conservative timing defaults without rewriting storage on load. Zero-to-60-second absences are economically credited; the one-minute threshold now controls only the return modal. `calculateOfflineEarnings()` is an idempotent compatibility adapter, not permission to backdate/replay arbitrary timestamps.

Unchanged limitations: JavaScript Number rounding, best-effort crash checkpoints, optimistic stale-tab protection, and no anti-cheat/security guarantee for a mutable client clock. Rolling back to older code restores old time bugs; do not strip timing metadata or restore already consumed resource/reward state. No per-frame/per-second offline replay or new dependency.

### Visible scheduling / presentation (Performance Fix V2)

- RAF cadence is not economic cadence. The existing eligible-frame sampler remains; passive `updateProduction()` runs at the existing heavy-work opportunities (120 ms desktop /180 ms mobile thresholds). Auto-buyer order/opportunities and Quest orchestration remain unchanged. A monotonic fallback keeps active settlement running through wall-clock rollback; it does not create extra auto-buyer opportunities.
- Settle actual elapsed time, never CPS divided by tick rate. Rate-changing actions, saves and lifecycle transitions still settle immediately. Pending time between passive ticks is settled at the next tick or mutation/checkpoint.
- Passive HUD is dirty/paced at 200 ms desktop /250 ms mobile. Balance/earned changes and boost countdown/expiry invalidate it; unchanged idle state does not repeatedly render. `updateDisplay()` defaults to coalesced next-frame action feedback; `updateDisplay(false)` marks passive work without scheduling another RAF. - Farm and resource-display checks retain their independent eligible-frame cadence. Closed Farm tab-body suppression remains. Existing title/Stats/DonutCoin/hidden-page polling is not redesigned.

### Hidden presentation lifecycle (Performance Fix V4)

- `canPresent()` requires a visible document and no lifecycle suspension. Presentation entry points sleep while hidden, including DOM tails called during required settlement. Economic reconciliation and chronology remain authoritative and never depend on this gate.
- One owner starts/stops title (1s), DonutCoin (1s) and Stats (5s) polling. Hide/pagehide cancels those intervals and pending HUD/main/tooltip/notification RAFs; autosave/action-save policy remains unchanged. Stats renders synchronously only when its desktop/mobile view is open, so no Stats RAF can accumulate. Each remaining presentation RAF owner must coalesce, cancel on suspension, or guard execution; do not queue background views.
- Suspend presentation before visibility settlement. On return, settle inactive time first, then refresh current HUD/store, open panels/quests/Stats, global care/mastery, countdowns, coin and title once; restart the existing visible scheduler/cadences. Duplicate pageshow/visibility events must not replay refreshes or inactive income. No focus/blur policy changes.
- Ordinary hidden notification history is not replayed; one pending critical storage-warning message is retained for return. Existing finite effect-removal, accepted-click quest and startup callbacks may finish. No presentation fields or timer handles enter saves.

## Production Math Contract (V1)

`getProductionBreakdown(now = this.getProductionQueryTime())` is the production entry point; `calculateProductionBreakdown()` contains the unchanged pure canonical formula. It returns per-building base/upgrade/recipe/boosted/flat rates and totals, plus global/prestige/quest/legacy factors. `calculatePerSecond()` and the read-only `totalPerSecond` getter expose its effective CPS; no mutable CPS cache is authoritative. Calculations use definitions and ownership, never DOM or previously multiplied `item.production` / `originalProduction`.

For building `i`: `localRate = baseItemProductions[i] × product(purchased normal building upgrade factors) × (1 + sum(recipe.craftCount × applicable productionBonus))`.

- Boosted CPS = `sum(count × localRate) × product(purchased donutUpgrades factors) × mastery × 2^prestigeCount × temporary`.
- Mastery is the existing `1.05` at farm mastery level 20+, otherwise `1`.
- Temporary = live quest factor × independent live legacy factors. Quest rewards have one active + one queued slot; queued rewards are not simultaneous factors. Expired rewards never affect a read; `updateQuestMultipliers()` owns cleanup/queue activation on economic ticks. The time settler activates a queued reward at the preceding reward’s actual expiry and integrates both lifetimes chronologically.
- Donut Cursor adds `0.1 × nonCursorBuildingCount` per owned Cursor **after all boosts**. This flat exception is also excluded from CPS-derived clicking. It is explicit existing behavior, including exemption from prestige.
- Effective CPS = boosted CPS + flat Cursor CPS. The time settler credits each chronological snapshot × eligible economic seconds to balance/run earned total and attributes the same per-building income to `totalProduced`. Old attribution totals are not rewritten.
- `getClickBreakdown()` / `calculateClickValue()` = `Cursor normal-upgrade product × temporary + boosted CPS × (0.01 × owned normal clicking-upgrade count) + flat Donut Cursor click bonus`. Temporary is already inside boosted CPS: do not multiply that term twice. Prestige/global bonuses affect the CPS term, not the manual base or flat bonus. The CPS fraction sums each normal clicking definition's `multiplier - 1` (currently 0.01 each); Auto Catcher is excluded from click-power counting; catches use canonical click value, with the existing 1.1 combo factor once.
- Crafting's flat donut payout keeps its existing `recipe.production × temporary` structure. Recipe building bonuses come only from craft ownership, not mutations to cached rates. No new main-game Farm PROD/COST/OFFLINE effects were activated; animal production remains separate.

All current CPS consumers (HUD, statistics, building panel, quests, farm CPS-based costs/rewards, offline donut earnings) use this authority. Stable quest history/median and frozen goals/rewards retain their existing policy. `getQuestClickEffortEstimate()` retains `1 + stableCPS × 0.005` as a legacy compatibility helper; Balance V1 recurring rewards use canonical click value and bounded human work instead. It is **not actual click power**. Existing frozen rewards/history are preserved; quest history selection now enforces its 120-second window on reads. When an old completed milestone lacks a frozen reward, loading calculates it only after full economic hydration and canonical cost restoration.

Compatibility: existing save version/formats and upgrade indices remain unchanged. Prestige, upgrade flags, recipe counts and timed rewards are restored as before; old stored rates and `productionMultiplier` are derived caches, not independent input. The latter field remains in snapshots for compatibility. `updateTotalPerSecond()`, `rebuildItemProductionsFromSaveState()`, `getFinalProductionMultiplier()` and `updateProductionMultiplier()` are adapters to the same model. The last multiplier API includes prestige/temporary only; **never multiply it into effective CPS**. Unpersisted `multiplierSources` and dormant farm/event factors were removed; they had no gameplay writers.

Old `activateMultiplier()` could dual-write a reward. For compatibility, ignore at most one legacy entry matching the live quest's amount and end time within 100 ms (consecutive old clock reads). Other legacy rewards still multiply and remain stored; new activations only use the queue. Old formats have no reward identity, so coincident independent rewards with this same signature are inherently ambiguous; do not broaden this heuristic casually.

`creditDonuts(amount, countsAsEarned = true)` is the common finite/nonnegative income gate. Preserve invariants: every modifier once; local bonuses remain local; flat exceptions stay flat; all CPS consumers agree; actual credited/attributed income reconciles; order/history and repeated rebuilds do not compound; save/load retains economic state; UI cannot change production. ### Recurring balance (V1)

Only new recurring assignments use the new target/reward policy. Milestone balance and all established lifecycle/render/claim contracts above remain. `dynamicQuestBalance` owns the per-difficulty constants:

| Difficulty | Planned work s | Base / max clicks | Max purchases | Reward rate | Cap baseline / max s | Purchase-cap fraction |
| --- | --- | --- | --- | --- | --- | --- |
| Easy | 60 | 80 / 120 | 3 | 10% | 3 / 15 | 10% |
| Medium | 180 | 240 / 360 | 5 | 12% | 9 / 45 | 15% |
| Hard | 360 | 600 / 800 | 8 | 15% | 18 / 90 | 20% |
| Special | 480 | 720 / 900 | 10 | 15% | 24 / 120 | 25% |

`getQuestBalanceContext()` consumes the canonical breakdown: reference CPS `C = min(effectiveCPS, boostedCPS / temporaryMultiplier + flatCPS)`. This is a conservative quest-planning projection of existing components, not a second production engine. It retains prestige/upgrades/recipes/mastery and the unboosted flat Cursor exception, while preventing expiring temporary boosts from inflating new work. Actual credited production is unchanged. Work rate `R = max(2, C)` supplies a startup proxy for two base clicks/sec when passive production is absent/tiny. Target snapshots do not subsequently move.

- Click goal = `ceil(min(maxClicks, baseClicks × (1 + 0.05 × (stage - 1))))`. Human timing assumes two deliberate clicks/sec, independent of CPS/prestige strength. Combo uses half that count plus `ceil(R × planned seconds)` production. Ordinary production/multiplier challenges also use `ceil(R × planned seconds)`.
- Timed production remains a short exception: `ceil(R × 45)` in the unchanged 60-second window. Manual startup earning makes a fresh timed goal attainable. Existing multiplier reward amounts/durations and all slot cooldowns are unchanged.
- Purchase budget = `R × seconds + 0.25 × min(balance, R × seconds)`. Plans account for escalating costs and cap quantity by difficulty. Any-building pricing uses a cheapest mixed basket, not average owned-building cost. Generation skips plans outside budget or worth less than 75% of planned work income, avoiding both infeasible and economically trivial assignments. Specific targets choose among eligible baskets; no building economics change.
- Spending target = `ceil(max(R × seconds, 2 × cheapest next building price))`; generation requires two cheapest purchases to fit the budget. Only actual building charges count, as before.
- Efficiency target = live CPS plus `min(max(0.1, 0.05 × live CPS), best affordable per-unit building CPS)`. The canonical per-unit rate makes one affordable building sufficient; any extra Cursor synergy helps. Generation excludes efficiency while a temporary production factor is active, or no strictly positive affordable gain exists.
- Generation retains existing slot pools/queue filtering and uniform choice among remaining candidates. It prefers unused exact types, then the least represented activity family (clicking / production / purchasing / efficiency). No viable choices falls back to existing production. It does not reroll an occupied slot.

Rewards use the difficulty rate on: production target; click effort `max(target × actual click value, C × target / 2)`; combo `1.2 × max(production target, clicks × actual click value)`; timed target ×1.2; efficiency `C × planned seconds`; purchase basket cost ×0.5; spending target ×0.3. Existing stage/difficulty floors remain. Recurring cap = `max(old floor, min(C × max cap seconds, max(next meaningful price × purchase fraction, C × cap baseline seconds)))`. The baseline raises only the cap, not every reward. Transaction rewards additionally cannot exceed `max(1, floor(cost × rate × 0.5))` for purchases / `max(1, floor(target × rate × 0.3))` for spending, so stage floors cannot create a profitable purchase loop. Final rewards are floored to whole donuts. Fresh-run rewards of 1 remain possible; old frozen rewards are never increased.

Balance compatibility is deliberately small: when loading an unfinished old click quest above its difficulty hard cap, clamp only that target and refresh its text; for combos clamp only the click component to half the cap. Keep identity, raw baselines/counters, production requirement and stored reward; normal progress checks still own completion/counting. Completed quests are untouched. Other old assignments remain frozen rather than being rerolled/repriced. Save version/formats are unchanged.

Regression coverage: `tests/quest-correctness.test.js` and 18 focused `tests/quest-balance.test.js` cases. Six deterministic fixtures live in `tests/helpers/quest-balance-fixtures.js`; estimates are not browser playtesting. Future product work may revisit cooldown pacing, old assigned non-click goals, very rapid purchases from banked cash and historical meta-counter semantics. Do not treat legitimate low rewards as corruption or inflate old frozen values.

## Mine / Ore Contract (Balance V1)

- **Reference:** `refreshOreMarketReference()` snapshots permanent production from authoritative `getProductionBreakdown()`: `C = boostedCPS / temporaryMultiplier + flatCPS`, `B = 2^floor(log2(C))` (roundoff tolerance at exact boundaries). With `W` Mines, `d = max(0, highest owned building index − Mine index)`, `s = max(.03, .20/(1+d))`, and retry-normalized base expected ore value `E = Σ(basePrice × rarity)/Σrarity`, scale = `(B/W) × 60s/(5E)`. Each ore reference `R = configured basePrice × scale`. Upgrades, recipes, prestige and permanent mastery enter through canonical production; quest/legacy temporary multipliers do not. This is a discrete planning snapshot, not a second CPS engine or per-frame price peg.
- **Holding protection:** references refresh only with **all ore stock empty**, after a Mine purchase (after its entire bulk loop) or before the next production batch. Held mined/purchased stock freezes the reference across upgrades, workforce changes and production, preventing upgrade→instant resale profit. Stock may retain an old reference until fully liquidated. Rebase empty-stock quotes at their prior quote/reference ratio, clamped to .5–2.5; reseed chart history so a new reference is not shown as trading growth. Initial new-run quotes start at reference. No automatic repricing on UI/rendering or ordinary sales.
- **Market:** per processed cycle, independent U,V: `T' = clamp(.85T + .4(U−.5), −1, 1)`; `x = ln(P)−ln(R)`; `P' = exp(ln(R) + .85x + v(.7T' + V−.5))`, bounded to `.5R…2.5R` for ordinary quotes. Volatility remains Copper .02 / Iron .035 / Gold .05 / Diamond .08. Thus displacement mean-reverts 15%/cycle, with existing momentum. Starting at reference, `|x| ≤ 1.2v/.15`, so even extreme ordinary paths do not reach the hard floor/ceiling; low quotes can still fall. No fee/spread. Non-finite arithmetic retains the prior valid quote; charts retain twenty valid samples and omit non-finite percentage changes.
- **Legacy transition:** old quotes/history/stock are preserved on load, including quotes outside the new band. Quotes outside the natural reachable envelope `|ln(P/R)| ≤ 1.2v/.15` are **sell only** and move monotonically toward ordinary range by at most 5%/processed cycle; no forced load-time haircut. The tooltip identifies transition quotes. Empty-stock rebasing may clamp outliers before new ore is generated, with no holdings affected. Do not enable purchases of artificially low recovery quotes.
- **Transactions/actions:** `transactOres()` validates all legs, positive finite prices, whole stock/unit deltas, funds, finite sums and allowance before commit. Buying is limited to one ore/unit per action, requires an actual finite nonnegative deduction and rejects transition quotes. Selling requires one successful `creditDonuts(value, false)` before inventory changes. Failed credit, invalid data, overflow or nonrepresentable changes consume neither inventory nor actions. **Ten market actions** per processed cycle: Buy one = one, Sell one = one, **Sell All full inventory = one** in visible ore order, atomically. Zero allowance sells nothing. This intentionally supersedes Correctness V1's one-unit/one-trade Sell All rule; no quantity selectors. Only a processed market cycle resets to ten; reload does not.
- **Recovery:** loaded finite nonnegative integral inventory is preserved; positive fractions floor; negative/non-finite/malformed counts become zero. Market entries recover invalid/nonpositive quotes to configured base, non-finite trends to zero, finite trends to [-1,1], history to its last twenty finite positive samples. No compensatory ore or unrelated repair. Runtime save candidates remain strict. Bad checksums, unsafe keys and unrelated structural corruption still use Save Integrity fallback/protection.
- **Accounting:** all ore-sale proceeds increase balance but exclude `totalDonutsEarned`, direct prestige eligibility and earned-production quest progress, preventing purchased/resold principal farming prestige. Ore purchases remain excluded from building-only spending tracking. No provenance system or Quest accounting changes.
- **Persistence/prestige:** optional `oreMarket: { referenceScale, productionBand, workforce, stage }` (or null) joins existing fields without changing save version/keys/envelope/checksum. Restore valid snapshots unchanged; absent/malformed reference defaults are initialized **after all economic hydration**, preserving legacy quotes/history/stock. Load-only malformed-reference recovery cannot poison strict backup/candidate validation. Existing write blocking, backup rotation, batching and stale-tab protection remain. Prestige clears reference/Mines/workers/stock, restores configured base prices/zero trends/empty history, ten actions and current checkpoint; permanent Farm mastery remains. Older clients ignore the optional field but retain old balance/transaction behavior; rollback needs no destructive migration and must not restore sold stock.

Reference-price/full-liquidation examples (not playtesting): first Mine 12.8%, early-mid 10.67%, mid 4.78%, late 1.89%, prestige8 early-run mix 16% of passive income. The unquantized stage shares .20 → .10 → .0667 → … → .03, combined with `B/C` approximately .5–1, keep new snapshots supplementary. Temporary buffs raise normal income without raising ore references. Common Copper retains the largest expected aggregate value; Diamond retains highest per-unit value/risk.

**Timing:** the shared settler processes complete Mine economic cycles at 100% visible / 25% inactive, preserving remainders and advancing the market/action reset once per cycle. Closed and hidden settlement match; the inactive episode has a continuous 12-hour economic cap. Existing global-boundary worker acquisition semantics remain. Each market advance remains one step; no market coefficients changed. Ore crafting/upgrades belong to future Mine/Ore Expansion. JavaScript Number precision/range remains; unrepresentable operations are rejected.

## Documentation Workflow

Before changing a major system, read its current contract here, the relevant entries in [PROJECT_HISTORY.md](docs/PROJECT_HISTORY.md), and the actual code. Documentation can be stale; do not substitute it for inspection.

After substantial work, update affected current-state contracts here and append a dated history entry recording the goal, previous behavior, why it changed, implementation/final behavior, important decisions, compatibility impact, verification, remaining risks/work. Do not log trivial edits. Record reality, not plans presented as completed work.
